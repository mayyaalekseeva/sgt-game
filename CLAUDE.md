# Barista Game

Mobile-first web app for baristas: dial in espresso/filter, diagnose mistakes, missions and ranks.
Portfolio project, non-commercial. Roaster: A Sargento (Torrefatora Lisboeta), used with permission.

## Stack

Vite + React 19 + TypeScript + Tailwind v4. Hash routing. EN/PT (src/i18n.ts, typed keys).
Runs as a single Cloudflare Worker (not Pages Functions): static assets from the Vite build plus a
Hono API on /api/_ (worker/, config in wrangler.jsonc, run_worker_first: ["/api/_"]).
D1 via Drizzle: schema in worker/db/schema.ts, SQL in migrations/ (generated by drizzle-kit, applied by
wrangler). Google sign-in (OAuth + PKCE) in worker/auth-routes.ts and worker/google.ts; sessions and
requireUser in worker/auth.ts (cookie stored only as SHA-256); client state in src/auth.tsx. Guests stay on
localStorage. Signed-in reports sync through /api/reports and /api/working-recipes (worker/reports.ts): ids
come from the client so re-sending is a no-op; the client caches per account and queues writes in an outbox
(src/sync.ts, src/reports.tsx). After filing, only a report's grinder and notes can change (PATCH, the later
editedAt wins); dose, yield, time, taste and diag never do, since the diagnosis and progress come from them. Deleting
keeps the id in deleted_reports so a late retry cannot file it again. Edits and deletes queue in the outbox too.
Screens read reports and progress from useReports, not useStore. Secrets GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET: .dev.vars locally, `wrangler secret put` in production.

## Scripts

- `npm run dev`: Vite dev server with the Worker running in the Workers runtime (one port)
- `npm run typecheck`: app (tsconfig.json) and Worker (tsconfig.worker.json)
- `npm test` / `npm run test:watch`: Vitest (vitest.config.ts, no Cloudflare plugin)
- `npm run build`: typecheck, then build to dist/client (app) and dist/barista_game (Worker)
- `npm run preview`: serve the build in the local Workers runtime
- `npm run deploy`: build, then `wrangler deploy`
- `npm run cf:types`: regenerate worker-configuration.d.ts after editing wrangler.jsonc
- `npm run db:generate`: write a new migration in migrations/ after editing worker/db/schema.ts
- `npm run db:migrate:local` / `db:migrate:remote`: apply pending migrations to D1
- `npm run db:seed:local` / `db:seed:remote`: load content/recipes.json into D1

## Rules

- Domain logic stays pure and UI-free: src/diagnose.ts, src/data.ts. Add tests for any change there.
- XP, rank and mission progress are derived from reports, never stored.
- Every user-facing string goes through i18n in BOTH en and pt.
- Design: sage #9AA784, cream #F1EDE0, ink #2C140A, olive #3F4F2E, terracotta #B5532F (accent only).
  Never cream text on sage. Fonts: Big Shoulders Stencil Display + Hanken Grotesk.
- Voice: the Sargento is warm, precise, never mocking. One change per brew.
- Recipes are guidelines (see docs/recipe-research.md), to be verified with the roaster.
- Recipe content lives in content/recipes.json (no admin UI). Versions are append-only: to change a
  recipe, add version N+1; never edit or delete a published version (reports reference `slug@version`,
  and the seed refuses changed versions). Archive with `"status": "archived"`.
- Espresso recipes are per roast (`espresso-medium`); filter recipes are per brewer (`filter-v60`) with a grind and
  timed steps, and no roast level: it will come from the coffee lot. The old per-roast filter recipes stay archived.
- Coffee lots live in content/lots.json (src/lots.ts), from the roaster shop. Reports store the lot slug, so never
  rename or delete a lot: retire it with `"status": "retired"`. Recipes are not per lot yet; the roaster will supply them.
  A lot's `photo` is the bag image on the shop's CDN; the app shows a resized copy in public/lots/<slug>.webp, made by
  `npm run lots:photos` (commit the file). Lots are shown on the "A Sargento coffees" screen with a link to buy.
- Players add their own coffees (src/coffees.ts; D1 `coffees`, synced like reports): roaster, origin, process, roast.
  Reports name them `my:<id>`. Every brew is of a coffee. Working recipes are per recipe and coffee (`workingKey`).
  Starting recipe: your working recipe for that coffee, else the roaster's, else the brewer/roast one (`forRoast`).
- Never edit an applied migration; change the schema and run `npm run db:generate`.
- Never commit secrets. Use .dev.vars locally and Cloudflare secrets in production.
- Design is mobile-first (390px). Desktop (1024px+) is a secondary adaptation: keep it minimal,
  don't add desktop-only features or redesign screens for it unless asked.
- Desktop from `lg` (1024px): sidebar nav (src/App.tsx) and two-column screens. Columns must keep the
  mobile stacking order, so below lg nothing changes. Also check changes at 1024px and 1280px.
- One feature per branch, small commits, run `npm test` and `npm run build` before committing.
